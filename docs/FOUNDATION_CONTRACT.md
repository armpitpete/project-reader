# Foundation Contract v0.1

## Purpose

Project Reader turns a GitHub repository into a calm, human-readable project page.

## Primary readers

- people who do not use GitHub;
- young people;
- neurodivergent people;
- collaborators, supporters, families, reviewers, and new contributors.

Clear language must not become childish language.

## First-screen contract

The first screen contains only:

1. Project name
2. What is it?
3. Status
4. Percentage complete
5. Likely chance of completion
6. What is done?
7. What is left to do?
8. One next step
9. View the project
10. How was this made?
11. Contact the project owner
12. Why these scores?

Anything more technical is secondary.

## Truth rules

- Never use commit count as a direct measure of completion.
- Never invent a finish line.
- Never hide uncertainty.
- Distinguish **confirmed**, **estimated**, and **unknown**.
- Every important claim must retain evidence.
- An owner-approved project profile outranks inference.
- Completion and likelihood of completion are separate measures.

## KISS rules

- One main idea per section.
- One next action, not a task wall.
- Plain outcomes instead of Git terminology.
- No architecture map on the first screen.
- No blank AI chat box as the primary interface.
- No repository writes in v0.1.

## Educational rules

For each important technology, explain:

1. What is it?
2. What does it do here?
3. Why was it used?
4. Where can I see it?
5. Why does it matter?

Offer three optional depths: **Simple**, **Learn more**, and **Technical**.

## Fun rules

Fun should come from discovery, clarity, small visual rewards, and understandable connections. It must not depend on noise, urgency, streaks, leaderboards, or compulsory gamification.
